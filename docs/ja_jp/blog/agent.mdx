## 作り出された「ブーム」

Agent 開発には、想像ほど多くの**独立ポジション**はない。熱狂のかなりの部分は、スクールや教材販売が不安を煽って作っている——まず怖がらせ、Agent レーンに飛び込ませる。

会社に入ってみると、RAG・Agent・LLM は、バックエンドエンジニアが少し調べ、Vibe Coding を一巡させれば、**デモできるもの**ができあがることが多い。ハードルは講座ほど高くない——ただし **デモを作る**ことと **運用可能・監査可能・スケール可能なものを出す**ことは別物だ。評価、権限、コスト、幻覚対策、既存システム連携——ここが人件費の大半になることが多い。

より正確な言い方は「Agent 需要がない」ではなく、需要が**下に沈んでいる**：既存のプロダクト、バックエンド、データ、セキュリティの役割に溶け込み、巨大な「Agent 開発業界」が単独で立ち上がるわけではない、ということだ。

## プロダクトの実態：データを詰めるだけで、需要は作らない

市場のアプリを見ると、表向きは AI 連携だが、ひと層剥くと多くは**データを入れて結果を出す**だけだ。

だから ToC Agent のスタートアップは深く伸びにくい——ToC に市場がゼロという意味ではなく（執筆、画像編集、伴走、汎用アシスタントに先例はある）、**多くのチームの ToC Agent は堀がなく、リテンションが弱く、課金習慣がつきにくい**。エンタープライズ側も同様で、Agent が要らない業務は多く、せいぜい RAG とスマートカスタマーサポート——需要の天井は見えている。

スマートカスタマーサポートは高度に手順化された仕事だ：モデル差し替え、マルチパス検索、解析モード、DB 差し替え——YAML を書き、OSS を写せば動く。標準化は「純粋な統合・写経」余地を圧縮するが、企業は**オンプレ、コンプライアンス、効果 SLA、業界データガバナンス**には依然払う——形は変わっても、一夜に消えはしない。

## 高給の幻想：アウトソース、要件の積み上げ、採用の混乱

### ポジションそのもの

Agent 職は給与が高く見えるが、分解すると**かなりの割合**がアウトソース名目の包装だ（不況期に正社員を外注化する大手も珍しくない）。一方でプラットフォーム、推論、オーケストレーション、セキュリティの正社員もいる——レーン全体をアウトソースと同一視してはいけない。

要件は積み上がる：フルスタックに LLM。だが Agent オーケストレーション自体はテンプレ化が進み、講座ほど継続開発できるシーンは多くない。Coding Agent、旅行プランニング、医療プランニング——業界内にいない、元々の実務者でないなら、途中参入は**ドメイン知識**と**運用経験**の二つを欠きがちだ。企業にとって、既存バックエンドの研究・異動の方が、「デモしか組めない」外注より得なことが多い。

### 求人プラットフォームのもう一つの混乱

Agent ブームに付随する、採用側の**演技的ミスマッチ**：

- JD が万能リスト：RAG、ファインチューニング、Agent フレームワーク、フルスタック、大手経歴、即戦力——給与帯は普通の開発並み；
- JD に合わせて履歴書を直し、キーワードとプロジェクトを揃え、システムは「マッチ度高」と表示；
- 一次が通らない、または HR が **「合いません」**——理由なし、または JD と噛み合わない（「0→1 の Agent プロダクト」が欲しいのに社内導入を書いた、「業務理解」が欲しいのに業界からの転職だった）。

これは単に「あなたが優秀でない」だけではなく、構造が重なる：

1. **本当に募集していない**：JD は人材プール、headcount 演出、内定済み枠の入口；
2. **JD は願望リストであって選考基準ではない**：書く人（HR/事業）と選ぶ人（HR/現場）のロジックが違う——アルゴリズムは語、人は「うちの人っぽさ」を見る；
3. **Agent 職名は大きく定義は曖昧**：同じ「Agent エンジニア」でも、prompt 調整の CS、IDE 開発、データラベリング——A 社 JD に合う履歴書が B 社では「不適」；
4. **供給過多の丁寧な断り**：「不適」が最安——「予算は外注のみ」「安い新卒が欲しい」と言うより楽。

結果：**求職者は JD に訓練されて投げ、HR は KPI に訓練されて選ぶ。プラットフォーム上で儀式は完遂するが、本当のマッチは減る。** 教材が不安を煽るのと同じ論理——外からは賑やか、中に入って初めてどのドアに鍵があるか分かる——誰も教えてくれない。

## Coding Agent：入場券は狭く、エンジニアリングは深い

Coding Agent はコンピュータ業界の知識だろう、という声もある。

Claude Code、Codex、Cursor、国内 Trae のようなチームに入れる人は極めて少ない。市場の多くは「AI で業務コードを書く」であって「AI IDE を作る」ではない。Vibe Coding のおもちゃプロジェクトから**プロダクション級** Coding Agent を引き継ぐのは遠い——コンテキストエンジニアリング、マルチファイル編集、diff、安定性、エンタープライズポリシー、チーム単位のデリバリーであり、「IDE のベテランが API を繋いだ」程度では代替にならない。

Vibe Coding しかできずエンジニアリング素養が弱い新人を採ると、コード理解と規範の補填、「生成してそのまま submit」の防止——レビューはシニアがツールを使うより遅くなることもある。

**業界を変えうるのは**「従来のエンジニアリング力 + 新しい AI 力」の複合体：システムと業務を理解し、LLM を既存ツールチェーンに組み込む人——フレームワークだけ知るドメイン外の主導者ではない。

## おわりに

Agent は**存在する**が、**語り過ぎ**られている。研修、JD、プラットフォームのマッチ度が「足りない、乗れ」と増幅する。

不安に流されず、三つ自問せよ：

1. 本当の問題を解くのか、「データを詰めて結果を出す」殻か？
2. 会社は**実装・統合**を採るのか、**ナラティブ上の AI ネイティブ**を採るのか？
3. JD と履歴書の「符合」はキーワード合格に過ぎず、枠が本当に空いていて基準が明確とは限らないのでは？

ここがはっきりすれば、Agent 講座をもう一つ受けるより、百通「高マッチ」の履歴書を投げるより、有用だ。
